rustc builds your program, then you run it. Relax runs your program while it builds it.

Relax is a live compiler and JIT runtime for Rust, written in Rust. It runs a Cargo package straight from source, with no rustc, LLVM or linker in the loop. It checks your code, compiles each function the moment it is first called, optimises the hot ones while the program runs, and patches new code into the running process when you save a file.

TL;DR Rust's speed and safety, without the compile-time wait.

  • What: a live compiler and JIT runtime for Rust that runs a Cargo package straight from source. No rustc, no LLVM, no linker.
  • Start: on an M4 MacBook a large 3D game shows its first frame 11 s after a clean checkout, where rustc builds for ~3 min first. The second run takes 1.15 s.
  • Change: save a file and the changed functions are patched into the running program, state kept. 92 tests re-run in 2.2 s.
  • Speed: optimised code is still slower than rustc --release. A broader run this week came out slower than our earlier numbers and we're re-measuring; see where LLVM still wins.
  • Size: one Rust library: 438k lines, 0 crates.io dependencies.

What it took: a new Rust toolchain, from source bytes to machine code

Relax isn't a wrapper around rustc or a plugin for LLVM. It replaces both, plus the parts of Cargo and the linker that sit between your source and a running program, in one Rust library with no dependencies.

Why this changes Rust

Rust gives you speed and safety, and charges for them in compile times. Relax keeps the speed and the safety and drops the charge.

With rustcWith Relax
Getting startedBuild everything first. On a large app, minutes pass before main runs.Start from source now. On an M4 MacBook a small app shows its first frame 3.7 s after a cold start, and a large 3D game in 11 s. Run them again and it's 0.41 s and 1.15 s.
Making a changeRebuild the crate and everything that depends on it, relink, restart, and get back to where you were.Saving is the build. Only the functions you changed are rechecked and recompiled, and they're swapped into the running program, which keeps its state, windows and connections.
Run-time speedFast, after a long optimised build.Fast, while it runs. Code starts on an interpreter and climbs to O1 and O3 in the background. Optimised Relax code is still slower than rustc --release (see where LLVM still wins).
SafetyEverything type- and borrow-checked.The same. Relax never runs code it hasn't checked.
Your cratesPath, git, crates.io, vendored, proc macros.The same crates, as written, procedural macros included.
CachesIncremental artefacts on disk that can go stale and need cargo clean.Every result is keyed by the hashes of its inputs. A hit is exactly what a fresh compile would produce. A warm start recompiles nothing.
When it's slowYou wait and guess.The runtime tells you. Every compile phase, stall and tier change goes to a flight recorder.

Built for AI agents: the loop that stays hot

An AI agent can't feel a slow build, but it pays for every one in tokens, wall-clock and lost context.

Edit reaches the programrebuild and relink: minutes on a large appsynced and patched in milliseconds (~50–200 ms to the box)

See the UIrebuild, relaunch, navigate backa frame of the live app, grabbed as a PNG

Makepad builds its apps with many AI agents working in parallel, each in its own lane, and Relax keeps them fast. Its dev hub, devhub, runs the build and test machines around Relax, so nothing an agent touches is ever cold:

flowchart LR
    A["AI agent<br/>edits a file"] -->|"sync, ~50-200 ms"| B["devhub<br/>routes to a warm box"]
    B --> C["Live Relax session<br/>patches only what changed"]
    C --> D["Tests re-run<br/>verdict in seconds"]
    C --> E["App frame<br/>grabbed as a PNG"]
    D --> A
    E --> A
    C -->|"flight recorder"| F["why it was slow,<br/>what it compiled"]
    F --> A
  • A live session per lane. Each agent's app or test run stays alive under Relax on a pool machine, and every save patches it. Nothing is rebuilt or relaunched.
  • Warm caches everywhere. Each machine refreshes its Relax cache as changes land, so a fresh worker starts warm.
  • No native builds in the loop. devhub sends iteration and pre-landing checks to Relax, and counts every native build that slips through, per lane.
  • Measured routing. Jobs are sized by their measured times, and quick checks go to machines with warm sessions, so they never queue behind a long build.

In practice: nine agent lanes run side by side, devhub handles more than 300 build and test jobs an hour, and dozens of changes land every day, each checked under Relax before it merges.

Procedural macrosBuilt as native dylibs, then loaded.Run natively when they match a linked build, otherwise on the JIT.

Native codeEverything is native.Crates that must stay native (OS layers, GPU, audio) export an interface with #[relax_api]. JIT code calls them through the C ABI planner, with per-thread heap routing across the boundary.

Back endsLLVM, then a system linker.Its own x86-64 and AArch64 code generators, with no linker and no LLVM.

Where LLVM still wins

LLVM has decades of optimisation work behind it, and in steady state its code is still faster than Relax's. Our own measurements: warm JIT against a native build of the same source and inputs, as wall-clock ratios (lower is better, 1.00× = LLVM).

WorkloadCPUvs --release, native CPUMeasured
3D-print slicer, first slice of a part, 4 threadsx86-64 (Zen 4)1.14× (cycles 1.15×, instructions 1.26×)2026-11-11
Same, 8 threadsx86-64 (Zen 4)1.17×2026-11-11
Same, 4 threadsAArch64 (Apple M4)1.24× (before this week's x86 gains were ported)2026-11-09

Dense numeric kernel (Cholesky factorisation)x86-64 (Zen 4)2.29×: LLVM vectorises it with AVX-512, Relax doesn't vectorise loops yet2026-11-10
Any workload against plain --release (portable CPU baseline)not measured yet

These are the workloads we profile most. A broader run of 18 workloads this week came out slower than these, and slower than in October; we're finding out why and will update this section with the result.

Which --release? Most Rust ships with plain --release, built for a portable baseline CPU (on x86-64, no AVX). Our numbers are against the harder setting, --release with -C target-cpu=native, where LLVM may use every instruction the machine has. Relax always compiles for the CPU it runs on, so against plain --release these gaps shrink, and on vector-heavy code they can flip. That comparison hasn't been measured yet.

Where the gap comes from, from instruction-level comparisons of the same functions. The gap is extra instructions rather than stalls: 1.26× the instructions cost only 1.15× the cycles.

CauseExtra instructions (slicer run)
Compares kept as bool registers and recomputed~25 G
Register copies (two-address form, coalescing misses)~23 G
Stack traffic: loop state kept in stack slots; 12 allocatable registers against rustc's 15~22 G
Extra loop-control and check branches, invariant tests left inside loops~13 G
Loads not folded into compares, i128 arithmetic, rematerialised constants, smaller items~33 G
Runtime outside the generated code (memcpy, allocator wrappers, TLS access, stubs)~40 G
No loop vectorisation, shallow unrollingmost of the numeric-kernel gap

What isn't a cause: inlining. Relax inlines more than rustc does.

Every row in this table is a work item, and the slicer gap went from 1.26× to 1.14× in the last three days.

Architecture

rustc hands your program to LLVM and a linker, and Cargo glues the steps together. Relax owns the whole pipeline, from source bytes to executable memory, in one process.

Relax is a stack of layers. Each layer is its own crate, builds only on the ones below it and re-exports them, so every module is crate::<module> at every layer. The layers compile in parallel, and a change in an upper layer never rebuilds the ones below.

A function's life

sequenceDiagram
    participant App as Running program
    participant RT as JIT runtime
    participant TY as Types layer
    participant CG as Codegen + backend

    Note over RT,TY: before the first call, every crate of the program is type-checked
    App->>RT: first call of fn f
    RT->>CG: compile f (interpreter or O1)
    CG-->>RT: machine code, published
    RT-->>App: call proceeds
    loop while f is hot
        RT->>CG: recompile f at O3 in the background
        CG-->>RT: faster code, swapped in
    end
    Note over App,RT: you save a change to f
    RT->>TY: recheck what changed
    TY-->>RT: ok
    RT->>CG: recompile f
    CG-->>RT: new code, the old code stays valid
    RT-->>App: next call runs the new f

With rustc, the same change is a rebuild of the crate, a relink and a restart.

Design rules

RuleWhat it means against rustc
Checked, then runSame guarantee as rustc: nothing runs unchecked. Relax just doesn't make you wait for the rest of the program first.
Never staleEvery cached result is keyed by the hashes of its inputs. A hit is exactly what a fresh compile would produce, so there's no cargo clean.
Code only growsPublished machine code is never freed or rewritten while it can still be on a stack. A swap publishes new code and redirects future calls, and is safe where a native hot-reload hack isn't.
Lazy by defaultrustc compiles everything you might call. Relax compiles what you do call, and optimises it in the background.
Rust as writtenOrdinary crates, from crates.io and git. libs/relax/KNOWN_GAPS.md lists what doesn't work yet.
InspectableEvery phase reports what it's doing; a stall can always be explained from its record.

Building

rustcRelax
To build itLLVM plus a bootstrapA stable Rust toolchain. Nothing from crates.io.
cargo build --release -p relax-compiler

The compiler is the relax_compiler library; relax (tools/run/runner) is its command-line runner.

Try it

From a fresh clone, build relax and run a new package through the JIT:

git clone https://github.com/makepad/relax
cargo build --release --manifest-path relax/Cargo.toml -p relax-runner --bin relax

cargo new hello
cd hello
../relax/target/release/relax run --quiet hello    # run main under the JIT
../relax/target/release/relax test hello           # run its #[test] fns
../relax/target/release/relax check hello          # type- and borrow-check only

Run relax in the package's folder and give it the package's name, not a path. It reads Relax's std from the checkout it was built in, so keep the relax folder where it is.

Each run also prints a makepad-remote: pid ... line: the running program's inspect socket (relax inspect).

Measured from a fresh clone: on a 16-core x86-64 Linux box, building relax took 53 s, the first relax run of hello 0.24 s and the next ones 0.01 to 0.07 s. On a 10-core arm64 Mac, with cargo held to 4 jobs, the build took 78 s, the first run 0.97 s and the next ones 0.03 to 0.04 s. Relax keeps what it compiles in the package's target/makepad-run, beside cargo's build output (120 to 190 MB for hello; relax clean removes it), so each new package starts cold.

Network. A package with no dependencies, like hello, needs none: it also runs with MAKEPAD_RUN_OFFLINE=1. For a crates.io dependency Relax takes the package from ~/.cargo's registry when it is there, and otherwise downloads it itself: the sparse index from index.crates.io and the .crate file from static.crates.io, checked against the index's SHA-256 and kept in that package's target/makepad-run. With cargo's offline setting (CARGO_NET_OFFLINE) or MAKEPAD_RUN_OFFLINE=1 it never downloads: a package whose dependencies it already fetched still runs, and one whose dependencies it has not fetched stops with an error naming the missing crate. relax fetch <git-url> (tools/run/runner/src/fetch.rs, also used by relax run <git-url> <package>) downloads a git repository over HTTPS into one store file under ~/.makepad-run (MAKEPAD_RUN_HOME); this repository is a 4 MB store.

Not everything runs yet: libs/relax/KNOWN_GAPS.md lists the open gaps, each with a repro.
